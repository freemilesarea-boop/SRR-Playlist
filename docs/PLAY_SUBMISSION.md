## 1. 결제 — 가장 흔한 반려 사유

구글 플레이 결제 정책은 **앱 안에서 파는 디지털 구독을 Google Play 결제로만**
팔게 하고, 외부 결제 페이지로 내보내는 것(링크아웃)을 금지한다. 우리 결제는
PayApp 웹 결제창이라 그대로 두면 반려된다.

그래서 **네이티브 빌드에서는 결제 진입점을 전부 감춘다.** 웹/PWA 는 스토어 정책
대상이 아니므로 아무것도 바뀌지 않는다.

판정은 `src/lib/purchaseGate.ts` 의 `canShowPurchaseUi()` 한 곳이다.
**새 결제 화면을 만들면 반드시 이걸로 감쌀 것** — `src/lib/purchaseGate.test.ts`
가 `res.payurl` 을 쓰는 파일을 전부 훑어서 게이트를 거치는지 검사한다.

| 막는 것 | 안 막는 것 |
| --- | --- |
| 요금제 카드의 가격·결제 CTA | 이미 결제한 사용자의 앱 이용 |
| `/pricing`, `/enterprise/pay` 화면 | 현재 구독 상태 표시 |
| 구독 유도 배너·모달의 결제 버튼 | **구독 해지** (오히려 열어두는 편이 안전) |
| 아티스트 대시보드 결제 카드 | 무료 체험 남은 기간 안내 |

> 결제할 수 있는 **다른 곳을 안내하는 것도** 반려 사유다("웹에서 결제하세요",
> 고객센터 링크 등). 그래서 안내 문구에 URL·연락처를 넣지 않았다.

나중에 앱에서 직접 팔고 싶으면 Google Play 결제 연동(수수료 15~30%) 또는
국내 개발자 제공 인앱결제(11~26%)를 붙여야 한다. 둘 다 링크아웃은 여전히 금지다.

## 2. 버전

**`package.json` 의 `version` 하나만 고친다.** 안드로이드/iOS 가 여기서 읽어 간다.

```
versionCode = major*10000 + minor*100 + patch      (1.0.0 → 10000)
versionName = package.json 의 version 그대로
```

Play 는 **같은 versionCode 를 두 번 받지 않는다.** 올릴 때마다 버전을 올려야 한다:

```bash
npm version patch   # 1.0.0 → 1.0.1
npm run aab
```

minor/patch 가 99 를 넘으면 versionCode 가 역전되므로 Gradle 이 빌드를 멈춘다.

---

> **versionCode 는 업로드를 시도한 것만으로 소진된다.** 플레이가 그 번들을
> 거부했든, 임시 출시를 삭제했든, 트랙에 올리지 않았든 상관없다. 한 번
> 올라간 번호는 영영 다시 못 쓴다("10000 버전 코드는 이미 사용되었습니다").
> 그러니 업로드가 거부되면 고친 뒤 **반드시 `package.json` 의 version 을
> 올리고 다시 빌드한다** — 같은 파일을 다시 올리는 것으로는 안 된다.

## 2-1. targetSdk

플레이는 **매년 8월 31일에 하한을 한 단계 올린다.** 2026-08-31 부터 신규 앱과
업데이트는 **API 36 (Android 16)** 을 타겟해야 하고, 미달이면 심사 이전에
업로드가 거부된다("API 수준 36 이상을 타겟해야 합니다").

바꾸는 곳은 `android/variables.gradle` 한 군데지만 도구 버전이 따라가야 한다:

| | 값 | 이유 |
| --- | --- | --- |
| `compileSdkVersion` · `targetSdkVersion` | 36 | 플레이 요건 |
| AGP (`android/build.gradle`) | 8.11.1 | 8.10 이하는 compileSdk 36 을 모른다 |
| Gradle 래퍼 | 8.13 | AGP 8.11 이 요구하는 하한 |
| `minSdkVersion` | **23 그대로** | 올리면 구형 매장 태블릿이 떨어져 나간다 |

`androidRelease.test.ts` 의 '플레이 SDK 요건' 이 네 값을 전부 잡는다.

내년 8월이면 37 로 또 올려야 한다. 그때는 위 표의 하한과 테스트의
`PLAY_MIN_TARGET_SDK` 를 같이 올린다.

### 36 으로 올릴 때 확인할 것

- **엣지 투 엣지** — 35 부터 이미 강제였고 36 은 예외 플래그를 없앴을 뿐이다.
  35 로 실기기 확인을 마쳤으므로 새로 생기는 위험은 아니지만, 상태바·네비게이션바에
  콘텐츠가 가리지 않는지 한 번 더 본다.
- **예측형 뒤로가기** — 36 타겟에서 기본 활성이다. 뒤로가기로 앱이 바로 종료되거나
  모달이 안 닫히는 동작이 없는지 확인한다.
- Gradle 래퍼가 바뀌었으므로 첫 빌드는 배포판을 새로 받느라 느리다.

## 3. 서명 키

```bash
npm run keystore
```

- 키(`android/deudda-release.jks`)와 비밀번호(`android/keystore.properties`)는
  `.gitignore` 에 있어 커밋되지 않는다.
- **이 둘을 잃으면 같은 앱으로 업데이트를 영영 올릴 수 없다.** Play 는 앱을 패키지
  이름이 아니라 서명 키로 식별한다. 만든 직후 비밀번호 관리자 + 외장 저장소에 백업.
- 스크립트가 SHA-1 / SHA-256 지문과 카카오 키 해시를 같이 뽑아준다.
  **이 릴리스 지문을 카카오·구글·Firebase 에 등록해야** 스토어 빌드에서 로그인이 된다.
  디버그 키로만 등록해두면 심사원이 로그인을 못 해서 반려된다.

지문은 세 군데에 등록한다. **디버그 키로 등록해둔 기존 값은 지우지 말고 추가만
한다** — 지우면 개발 빌드에서 로그인이 깨진다. 지문을 잊었으면
`npm run keystore -- --print` 로 다시 뽑는다.

| 등록할 곳 | 화면 | 넣는 값 |
| --- | --- | --- |
| 카카오 개발자 | 내 애플리케이션 → 플랫폼 → Android | 패키지명 `com.deudda.app` + **카카오 키 해시** |
| Firebase | 프로젝트 설정 → 내 앱(Android) → 디지털 지문 추가 | **SHA-1 과 SHA-256 둘 다** |
| Google Cloud | API 및 서비스 → 사용자 인증 정보 → Android OAuth 클라이언트 | 패키지명 + **SHA-1** |

Firebase 에 지문을 넣은 뒤 `google-services.json` 을 다시 받을 필요는 없다
(지문은 서버 쪽에서 대조한다). 구글 로그인이 `DEVELOPER_ERROR` 로 떨어지면
거의 항상 이 등록이 빠진 것이다.

> 지금 기기에 깔려 있는 `deudda-1.0-debug.apk` 는 **디버그 키**로 서명돼 있다.
> 릴리스 빌드는 그 위에 안 깔린다(`INSTALL_FAILED_UPDATE_INCOMPATIBLE`) —
> 한 번 지우고 다시 설치해야 한다.

## 4. Play Console 계정

등록비 **$25 (1회)**.

**이 프로젝트는 개인 계정이다.** 그래서 프로덕션(정식 출시) 권한을 열려면
**비공개 테스트에 테스터 12명 이상이 14일 연속 참여**해야 한다. 조직(사업자)
계정은 이 규칙이 없지만, 조직 계정은 **D-U-N-S 번호**가 있어야 만들 수 있어
지금 당장 바꿔 쓰기는 어렵다(발급에 며칠~몇 주). 계정 유형 변경 절차는
Play Console 지원팀에 확인해야 한다 — 보통 새 조직 계정을 만들어 앱을
이전하는 쪽이다.

### 트랙 세 개의 차이

| 트랙 | 심사 | 인원 | 14일 규칙 |
| --- | --- | --- | --- |
| **내부 테스트** | 거의 없음, 몇 분이면 배포 | 100명 | **카운트 안 됨** |
| **비공개 테스트** | 첫 버전은 심사 있음(수일) | 제한 없음 | **여기서만 카운트** |
| 프로덕션 | 정식 심사 | 전체 | — |

핵심: **내부 테스트만 아무리 돌려도 14일 시계는 시작되지 않는다.** 그러니
두 트랙을 동시에 쓴다 — 내부 테스트로 점주에게 오늘 배포하고, 같은 `.aab` 를
비공개 테스트에도 올려 시계를 돌린다.

### 12명 × 14일, 실패하는 지점

- **"참여(opt-in)한" 테스터 수**로 센다. 이메일 목록에 넣기만 해선 안 되고
  각자 초대 링크를 눌러 수락해야 한다.
- 14일 **연속**이다. 중간에 11명으로 떨어지면 카운터가 리셋된다.
  → **15~20명 모아둘 것.** 여유분 없이 딱 12명은 거의 실패한다.
- 테스터는 구글 계정(Gmail)이 필요하다.
- 14일이 지나면 자동 승인이 아니라 **프로덕션 액세스 신청서**를 따로 낸다.
  테스트 중 뭘 배웠는지 적는 칸이 있고, 심사에 며칠 더 걸린다.

→ **시계부터 돌려라.** 스토어 등록정보·스크린샷은 그 2주 안에 하면 된다.

## 5. 앱 콘텐츠 선언 (Console → 정책 → 앱 콘텐츠)

### 포그라운드 서비스 용도

`mediaPlayback` 을 쓰므로 선언 양식이 뜬다. 짧은 영상(또는 설명)으로
**"매장에서 화면을 끄거나 다른 앱을 쓰는 동안에도 배경음악이 계속 재생되어야 한다"**
는 점을 보이면 된다. 기능이 앱의 핵심이라 통과 난이도는 낮다.

### 데이터 보안 (Data safety)

> 마법사 2단계 **"필수 사용자 데이터 유형을 수집하거나 공유하나요?" → 예.**
> 기본값이 '아니요'라 그냥 넘기기 쉬운데, 이건 허위 선언이 되고 적발 시
> 반려가 아니라 **앱 삭제·계정 제재**다.

3단계(데이터 유형)에서 아래만 체크한다. 코드 기준이며
`src/pages/legal/PrivacyPage.tsx` 와 어긋나면 안 된다.

| Play 카테고리 | 하위 항목 | 우리 쪽 근거 |
| --- | --- | --- |
| 개인 정보 | 이름 | `users.full_name` |
| 개인 정보 | 이메일 주소 | 로그인 ID |
| 개인 정보 | 사용자 ID | `users.id` (Supabase uuid) |
| 개인 정보 | 주소 | `users.address` |
| 개인 정보 | 전화번호 | `users.phone` |
| 개인 정보 | 기타 정보 | 생년월일, 사업자 정보 |
| 금융 정보 | 사용자 결제 정보 | 구독 결제(PayApp) |
| 오디오 파일 | 음악 파일 | 아티스트가 올리는 음원 |
| 앱 활동 | 앱 상호작용 | 재생 이력 |
| 앱 활동 | 인앱 검색 기록 | 검색어 |
| 앱 정보 및 성능 | 비정상 종료 로그 · 진단 | Sentry (`src/lib/sentry.ts`) |
| 기기 또는 기타 ID | 기기 또는 기타 ID | FCM 푸시 토큰 |

**체크하지 않는 것**: 위치 · 연락처 · 사진/동영상 · 캘린더 · 메시지 ·
건강/피트니스 · 웹 검색 · 설치된 앱. 권한 자체가 없다(INTERNET ·
WAKE_LOCK · POST_NOTIFICATIONS · FOREGROUND_SERVICE 뿐).

4단계(데이터 취급 및 처리)에서 항목마다 묻는다:

| 항목 | 수집 | 공유 | 필수/선택 | 목적 |
| --- | --- | --- | --- | --- |
| 이름 · 이메일 · 사용자 ID | 예 | 아니오 | 필수 | 앱 기능, 계정 관리 |
| 기타 정보(생년월일·사업자) | 예 | 아니오 | 필수 | 앱 기능, 계정 관리 |
| 주소 · 전화번호 | 예 | 아니오 | 선택 | 앱 기능, 계정 관리 |
| 사용자 결제 정보 | 예 | 예 | 선택 | 앱 기능 |
| 음악 파일 | 예 | 아니오 | 선택 | 앱 기능 |
| 앱 상호작용 · 검색 기록 | 예 | 아니오 | 선택 | 앱 기능, 분석 |
| 비정상 종료 로그 · 진단 | 예 | 아니오 | 선택 | 분석 |
| 기기 또는 기타 ID | 예 | 아니오 | 선택 | 앱 기능 |

- **전송 중 암호화: 예** (전 구간 HTTPS)
- **사용자가 삭제 요청 가능: 예** (앱 내 회원 탈퇴 — `ProfilePage`)
- 카드번호를 직접 보관하지 않는다. PayApp 이 처리한다.

> **"공유"의 정의에 주의.** 구글은 *우리를 대신해 처리하는 수탁업체*로의
> 전달은 공유로 치지 않는다. 그 기준이면 PayApp 도 Sentry 도 '아니오'가
> 맞다. 결제만 '예'로 둔 것은 돈이 오가는 쪽을 보수적으로 잡은 것이다 —
> 넓게 선언해서 문제가 되는 일은 없지만 좁게 선언한 것이 틀리면 제재다.

> **Sentry 는 DSN 이 있을 때만 동작한다**(`VITE_SENTRY_DSN`, production 빌드).
> 빌드한 `.env` 에 값이 비어 있으면 실제로는 아무것도 보내지 않는다. 그래도
> 선언해 두는 쪽을 권한다 — 나중에 DSN 을 켜는 순간 선언이 틀려지고,
> 안 하는 일을 선언하는 것은 제재 사유가 아니다.

### 그 외

- **광고**: 없음
- **콘텐츠 등급**: 설문 응답 기준. 음악 스트리밍이고 사용자 간 소통 기능이 없으면 전체이용가
- **타깃 연령**: 만 13세 이상 (아동 대상 아님 — 실수로 '아동 포함' 을 고르면
  Families 정책이 걸려 심사가 크게 늘어난다)
- **정부 앱 / 금융 앱**: 아니오

## 7. 제출 순서

개인 계정 기준이다(§4). 14일 시계가 전체 일정을 결정하므로 **시계를 먼저 돌린다.**

1. ✅ `npm run keystore` → 지문을 카카오·구글·Firebase 에 등록 (§3)
2. Supabase 대시보드에 `com.deudda.app://auth/callback` 추가
   — 안 하면 앱에서 소셜 로그인이 안 되고 심사원도 못 들어온다
3. 앱 만들기 → 패키지명 `com.deudda.app`
4. `npm run aab` → **내부 테스트** 업로드 → 점주에게 링크 전달 (오늘 가능)
5. 같은 `.aab` 를 **비공개 테스트**에도 올리고 테스터 15~20명 초대
   → **12명이 수락한 날부터 14일 카운트 시작**
6. 그 2주 동안: 앱 콘텐츠 선언 (§5) · 스토어 등록정보 (§6) · 스크린샷
7. 14일 경과 → **프로덕션 액세스 신청** → 심사
8. 프로덕션 출시

**3~5번은 5·6번이 끝나기 전에도 된다.** 먼저 올려두는 편이 빠르다 —
업로드하면 그 자리에서 걸리는 문제(서명, targetSdk, 권한)를 알려준다.

> 점주 배포가 급하면 **4번에서 이미 끝난다.** 내부 테스트도 Play 스토어를 통해
> 설치되고 자동 업데이트도 된다. 7·8번은 "아무나 검색해서 받을 수 있게"
> 하려는 단계다.
